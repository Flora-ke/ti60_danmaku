# Ti60／Sapphire 硬件游戏接入

## 当前入口与三种模式

推荐 `platform/accelerated_main.c`，通过 `make board` 构建。它复用游戏逻辑、公共命令生成器、CPU context，以及runtime真实G2D／FRM会话。游戏400×300居中在640×480输出的`(120,90)`，没有缩放或削减弹幕。

| 按键 | 工作方式 |
|---|---|
| 1 | CPU画自有640×480 RAM，G2D全屏Copy到硬件分配帧后显示 |
| 2 | 场景全部Fill／Copy／CopyKey由G2D执行并显示 |
| 3 | 同一冻结命令先走CPU＋搬运，再走原生G2D，先后确认两帧 |

默认模式1、新手标题界面。后端选择与新手／标准、低／中／高强度独立，不改变Game／哈希。请求只在当前任务完成并release后的IDLE生效；模式3必须完成一对结果后切换。等待硬件期间继续服务输入和逻辑，CPU同步绘制或总线阻塞本身不保证60Hz实际运行速率。

模式1仍使用硬件搬运显示；模式3不是并排或加速比演示。画面内容应一致，串口mode／req、shown／pair及gpu_frame可确认实际路径。

## 匹配硬件与启动前提

实际引用 `D:\Desktop\2026FPGA\bitblt_soc-ysl-dev\embedded_sw\newSoC`；硬件／BSP只读。依据为该目录的 `soc.h`、`bsp.h`、`soc.mk`、standalone启动／驱动、生成CPU及G2D／显示RTL，详细协议见同级runtime的 `HARDWARE_ADAPTATION.md`。

| 项目 | 当前事实 |
|---|---|
| CPU／ABI | RV32IM、Zicsr／Zifencei、ILP32，无MMU／FPU |
| CLINT | `BSP_CLINT`，100MHz，`clint_getTime`高低高读取 |
| UART | `BSP_UART_TERMINAL`，115200／8N1，FIFO128B |
| D-cache | 4KiB、单路、64B行、写穿 |
| G2D／FRM1 | `0xF8101000`／`0xF8102000`，当前ABI／CAPS由probe核对 |
| 硬件显示帧 | 640×480 RGB565，stride1280B；A=`0x01000000`、B=`0x01100000`，各完整1MiB预留 |
| CPU共享DDR | 实际安全窗口`[0x1000,0x10000000)`，CPU与设备地址显式绑定 |

运行前由集成者确认：板上是匹配普通CPU位流；DDR已经初始化／校准；应用区和硬件帧区独占；加载器完成所有LOAD段后启动；CPU、G2D、显示处于协调冷态。构建哈希与设备ABI探测不能证明板上位流恰好来自当前源码。

不能只重启CPU或重新加载BSS来解除仍在运行的G2D／显示访问。最终FRONT继续属于显示端，程序退出／控制端退出不等于停显或租约归还。

## RAM构建与证据

```sh
cd /mnt/d/Desktop/2026FPGA/ti60_danmaku
make board
# 移动目录时显式提供三个外部依赖路径：
python3 tools/build_sapphire.py \
 --gfx-root /mnt/d/Desktop/2026FPGA/bitblt-runtime \
 --soc-root /mnt/d/Desktop/2026FPGA/bitblt_soc-ysl-dev/embedded_sw/newSoC \
 --riscv-bin /mnt/d/Desktop/2026FPGA/bitblt-runtime/build/toolchains/xpack-riscv-none-elf-gcc-14.2.0-3/bin/riscv-none-elf-
```

需要已有WSL／Linux、Python、GNU Make和裸机工具链；脚本不下载或安装工具。板端采用真实BSP，未链接SDL、Windows／Linux host运行支持。产物只写游戏 `build/sapphire/`：ELF／map／bin／hex／asm、构建命令与 `build_manifest.json`。该命令不加载、运行或烧写产物。

构建器在运行前核对runtime `platform/sapphire/publish_contract.json`的12个RTL/BSP文件哈希，构建后再次核对；任何不匹配均失败，不能删除校验来强行生成成功记录。它另检查ELF32小端RISC-V、LOAD位于应用区、自有DMA／排空数组的BSS归属与64B对齐、发布指令和栈，并检测构建期间源码变化。

`platform/game_ddr.ld`专门预留应用`[0x1000,0x201000)`共2MiB，栈64KiB，启动符号匹配厂商 `start.S`。默认124KiB应用区／4KiB栈不适合该游戏；DDR必须在startup清BSS前可用，不能在main里补救。这里是RAM加载布局，不是Flash／XIP布局。

| 关键自有存储 | 字节 |
|---|---:|
|打包11个图片／字库源|252672|
|CPU画布640×480×2|614400|
|CPU context预留|90112|
|G2D context精确／预留|126504／128512|
|应用栈|65536|

生成命令数组、库内快照、编码和预检表都已计入各对象／工作区。一次已完成链接占用1565248B／2097152B，约74.64%；最终以manifest的 `memory_bytes_from_origin`、workspace_symbols、owned_bss及map为准，不把上表当完整占用。原素材／三色字库常量仍在ELF，上传后有独立DMA副本。硬件A/B显示帧不放入应用BSS。

## 素材发布和显示所有权

初始化为11个源分配64B对齐片段，每行stride向16B对齐，每个源尾补足DMA和缓存行；先校验全部范围／CPU与设备别名，再上传原RGB565像素。另将自有CPU画布注册为第12个只读DMA源。两后端消费相同源视图。

匹配写穿CPU的发布实现位于runtime `platform/sapphire/cache_publish.c`：实际全D-cache失效指令`0x0000500F`，随后独占DDR行的强制读miss，利用已核对BMB／AXI桥的同source写响应排序排空之前CPU写入，再维持MMIO顺序。不是调用未实现的CSR0x810，也不是空clean回调。实际桥定向验证609项通过；这不等于整CPU／DDR／显示链板测通过。

发布器只处理CPU拥有且设备只读的源，不提供DMA目标读回acquire。CPU不写硬件FRONT，不通过FREE状态推测CPU读所有权，也不读取硬件FRONT进行像素对比。模式1通过G2D Copy发布CPU结果，因此无需假造CPU直接PRESENT寄存器。

同一设备与FRM捕获者由一个context独占。每个job执行BEGIN→硬件分配目标→成功全屏Fill→原序绘图流→END→render／presented／health确认→旧front释放；硬件内部完成呈现握手。软件没有任意目标地址配置、PRESENT、停显或协调复位接口。

CPU画布在被DMA读取期间不能改写；模式3先完成CPU搬运job并release，再使用同一冻结命令执行原生job。失败或超时保留job、源、工作区及帧租约；FAILED可能仍返回release BUSY。入口记录STOP并停止推进，不自动补END／重提／复位／回退CPU。

软件帧预算为5秒，但它只能约束能返回的软件轮询。DDR永久无响应时，同步排空读或MMIO可能不返回，软件超时不能抢占该总线访问。发生此情况须保留调试现场并按真实硬件协调恢复流程处理。

## UART键盘协议

用本游戏 `tools/uart_bridge.py`发送CRC按键快照。runtime原文本行控制工具协议不同。串口115200、8数据位、无校验、1停止位，约30Hz发送完整状态：

| 字节 | 含义 |
|---:|---|
|0、1|帧头`A5 5A`|
|2|版本`01`|
|3|负载长度`03`|
|4|序号，0..255循环，仅诊断|
|5、6|小端16位按键位图|
|7|对字节2..6算CRC-8，poly07、初值0、无反射／最终异或|

bit0..9为左／右／上／下／射击／开始／暂停／演示／强度／难度，bit10／11／12为CPU／G2D／比较。允许位图`0x1FFF`，未知位整帧拒绝，8字节布局未变。零报文仍为`A5 5A 01 03 00 00 00 58`。

仅完整正确帧更新状态；半帧间隔超过100ms丢弃，250ms没有有效帧释放全部键，坏帧不续租。每轮最多接收64字节。单独1／2／3的上升沿选择后端，持续按住不重开；同时按多个后端键维持当前选择，松开后再单独按。渲染选择位在调用game_step前被剥离，不影响Game哈希。

Windows PowerShell示例，COM6须换真实端口：

```powershell
cd D:\Desktop\2026FPGA\ti60_danmaku
py tools/uart_bridge.py --self-test
py -m pip install pyserial
py tools/uart_bridge.py --port COM6
```

pyserial只用于电脑端；自测不开串口。Windows默认仅当前启动终端获得焦点时采样真实按下／松开，支持同时移动和射击，失焦发零；WASD／方向移动，Z／空格按住射击，Enter／R重开，P暂停，M演示，K强度，N难度，1／2／3后端，Q／Esc／Ctrl+C退出并尽力发送释放。主机短写或异常会报错，不等于板端收到释放确认；板端超时释放作为补充。

Linux命令为 `python3 tools/uart_bridge.py --port /dev/ttyUSB0`，终端重复键使用180ms租约，不能可靠表达真实松键，空格切换持续射击。Windows `--terminal`也使用该模式。SDL预览键位略有不同：D演示、Tab强度，2／3明确提示无硬件。三者最终使用同一游戏按键定义。

## 节拍、遥测与验收

逻辑固定60Hz步长，目标每秒30次场景提交。调试暂停／过载时最多追赶8步，超出的积压计入late并丢弃，不能将目标节拍写成实测帧率。暂停不推进游戏保护时间、子弹或攻击冷却；结束后Enter直接重开并恢复所选配置。新手十命／180tick／自动射击，标准三命／120tick／按键射击，弹幕规则不变。

遥测值为十六进制：mode是当前实际后端，req是请求，tick是游戏逻辑步，shown累计实际确认呈现，pair累计完成比较对，cmds当前场景命令数，late积压计数。cpu_draw为CPU绘制区间，cpu_seq标识CPU完成序号；gpu_frame标识最近原生硬件帧，gpu_valid／gpu_error指出其计时是否可用，无效为NA。gpu_total包括原生软件准备／缓存／提交轮询及执行、呈现、健康观察等待；gpu_present仅其中呈现等待部分。它们不是硬件内部周期，不能直接与CPU draw相除宣称加速比。

主机已验证全画布参考像素、软件解码协议、跨模式会话和完整高档演示；RAM ELF已构建并检查。实际UART／按键焦点、匹配位流DDR、G2D像素、HDMI显示与板上性能仍待现场验收，具体证据和最终复验结果见 `PROGRESS.md`、`build/validation.json`及`build/sapphire/build_manifest.json`。

建议板测依次确认：位流／DDR／冷态与应用预留→按既有RAM流程加载本ELF→输入1观察CPU结果和呈现计数→2核对同场景→3核对比较对／两次呈现→高档完整演示及暂停／重开→保存串口日志和manifest。故障先取证，不能通过仅重启CPU或清空BSS恢复。

## 历史入口

`platform/sapphire_main.c`保留原CPU／`RAM_ONLY_DIAGNOSTIC`及外部 `board_video_*`／`board_g2d_*`契约；默认视频未适配仍明确返回不可用。`g2d_scene.[ch]`与`BOARD_G2D_ADAPTER_EXTERNAL`属于旧游戏专用接口，详见[g2d_scene.md](g2d_scene.md)。它们未用于当前公共后端／ELF，也不用于本轮公平比较。

`make board-check RISCV_CC=... SOC_ROOT=...`继续提供源码检查，包括保留入口及新入口；它与生成RAM ELF的`make board`是不同操作。旧记录中的“本轮不生成ELF／只有CPU”是当时边界，当前已由上述新入口更新。
