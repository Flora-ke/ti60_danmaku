# Ti60 / Sapphire 板卡接入说明

## 交付边界

这里提供可供 Sapphire 裸机工程集成的 C 源码，游戏逻辑、RGB565 CPU 绘图、UART 输入和 CLINT 调度都已落地。未生成 ELF，未烧写、未测量板上帧率。此版本使用 CPU 绘制全部像素，不能作为 FPGA G2D 加速效果的证据。

当前已知工程的显示/G2D 控制尚不完整。默认 `board_video_init()` 返回 `BOARD_UNAVAILABLE`，入口经 UART 输出错误后停住，保留状态，绝不假装已经显示游戏。必须实现真实视频适配器，或显式定义 `RAM_ONLY_DIAGNOSTIC` 进行没有视频输出的 DDR 运算诊断。

## 实际核对的 BSP

只读核对目录：`D:\Desktop\2026FPGA\bitblt_soc-main\embedded_sw\newSoC`。

| 源文件 | 本程序采用的事实 |
|---|---|
| `bsp/efinix/EfxSapphireSoc/include/soc.h` | RV32IM，无 FPU/MMU；CLINT 100 MHz；UART RX/TX FIFO 各 128 字节；4 KiB D-cache，64 字节 cache line |
| 同目录 `bsp.h` | `bsp_init()` 设置 UART 115200、8N1；采用 `BSP_UART_TERMINAL`、`BSP_CLINT`、`BSP_CLINT_HZ` |
| `software/standalone/driver/uart.h` | `uart_readOccupancy()` 可非阻塞判断 RX；读取 `UART_DATA` 消费字节；TX availability 允许有界发送 |
| 同目录 `clint.h` | `clint_getTime()` 高低高读取，防止 RV32 低字溢出时读到错误时间 |
| `software/standalone/common/start.S` | 设置栈，复制 `.data`、清零 `.bss`，默认调用 `__libc_init_array`，之后进入 `main` |
| `bsp/.../linker/default.ld` | 默认仅 124 KiB 应用区，默认栈 4 KiB；不能容纳本程序的双帧缓冲 |

`soc.h` 的 DDR 窗口描述为 `SYSTEM_DDR_BMB=0x1000`、大小 `0x10000000`。这是配置证据，不能据此认定任意一段 DDR 均归游戏独占。当前位流、加载器保留区和实际 DDR 初始化顺序仍需由集成者核对。

## 文件作用

- `platform/sapphire_main.c`：实际 BSP 入口；唯一 UART RX 消费者；固定 60 Hz 逻辑、目标 30 Hz CPU 渲染、每秒 UART 统计；静态保留两张 400×300 RGB565 帧。
- `platform/board_port.c`：与 BSP 无关的 UART 帧解析、CRC 和超时释放；显示未接入时的显式失败实现。
- `include/board_port.h`：串口协议和视频所有权契约。
- `tools/uart_bridge.py`：电脑端控制工具；不下载程序、不烧写；使用串口发送完整按键状态快照，同时显示遥测。
- `tests/test_board_uart.c`：可在电脑运行的协议测试，包含断帧、CRC 错误、未知按键、重同步、计时器回绕、释放及默认显示失败测试。

## DDR、栈与启动集成

帧缓冲占 `2 × 400 × 300 × 2 = 480000` 字节，按 64 字节对齐；`Game` 也作为静态对象，不放在 4 KiB 栈上。帧缓冲没有指定物理地址，由经过确认的链接布局放置。游戏对象、资源和代码的准确大小应通过本项目的内存报告及之后真实链接的 map 文件核实。

集成时必须：

1. 保留同一套 Sapphire BSP、`start.S`、厂商工具链和 C 库；将本项目公共源文件、`board_port.c`、`sapphire_main.c` 加入应用，排除 SDL/host 的 `main`。
2. 为整个应用显式预留不少于规划预算的 DDR 区域，并验证加载器和调试下载确实能写入该区域。不要继续使用默认 124 KiB 链接区。
3. 核实 linker 中 `_data_lma/_data/_edata/__bss_start/_end/_sp` 等启动符号与真实 `start.S` 一致。若保留 `__libc_init_array`，须正确链接 C 运行库；不可删除报错来假装适配成功。
4. 验证零化 `.bss` 时 DDR 已经可访问。两张帧在进入 `main` 前会被清零；这不能靠 `main` 里的初始化补救。
5. 使用本 BSP 声明的 RV32IM ABI，不依赖浮点扩展；需要编译器运行库实现 64 位整数除法。板卡入口采用 `-std=gnu11`，因为原 BSP 头文件使用 GNU `asm` 扩展；公共游戏和协议逻辑仍可严格 C11。当前源码无需堆分配，仍需 C 库提供 `memset` 等公共函数。
6. 本轮只准备源码和检查项，不自动修改厂商 BSP，不生成或下载 ELF。

## 视频适配器必须完成的任务

正常出屏模式定义 `BOARD_VIDEO_ADAPTER_EXTERNAL`，并链接自有实现：

```c
int board_video_init(uint16_t *buffer0, uint16_t *buffer1,
                     unsigned width, unsigned height, size_t stride_pixels);
int board_video_acquire(unsigned *index);
int board_video_present(unsigned index);
```

调用顺序为初始化→获取可写缓冲→CPU 绘图→提交显示，循环重复。

- 适配器接收 CPU 指针、尺寸和以像素为单位的步长；不得默认 CPU 指针必然等于设备总线地址。
- `acquire` 仅交还显示端已释放的帧，索引只能为 0 或 1，绝不能让 CPU 覆盖仍被扫描的缓冲。
- `present` 必须完成真实缓存清理和设备可见性保证，再由已验证的显示控制协议接收。当前 BSP 配置启用了 D-cache，UART/CLINT 正常不代表 DMA 自动一致。不能凭空填入未知的 cache 指令。
- 显示端须支持 RGB565、400×300，或显式完成格式转换和缩放。若最终输出 800×600，应由实际显示链完成 2×放大；本程序没有偷偷分配第三张 800×600 帧。
- 以适配器返回 `BOARD_OK` 表示契约已满足；BUSY/错误当前均停止主循环并保留状态，不绕过为“成功”。支持异步排队时请在适配器内实现有界等待和错误处理。
- 此处没有 G2D 的寄存器地址、命令或缓存假实现。将 CPU renderer 改成硬件绘制，需另依据实际验收后的 G2D ABI 接入。

没有显示硬件时，显式编译 `RAM_ONLY_DIAGNOSTIC`。此模式完全绕过显示接口，循环把画面写到两个 DDR 数组并输出遥测。它可以验证逻辑、UART、计时和 RAM 渲染路径，**不能验证视频输出、G2D、DMA 缓存一致性、撕裂或板上显示 FPS**。

## UART 按键协议

115200 baud，8 数据位，无校验，1 停止位。输入端每 33 ms（约 30 Hz）发送完整状态：

| 字节 | 含义 |
|---:|---|
| 0、1 | 固定帧头 `A5 5A` |
| 2 | 版本 `01` |
| 3 | 负载长度 `03` |
| 4 | 序号，0～255 循环，仅便于识别，不用于拒绝电脑重启后的报文 |
| 5、6 | 小端 16 位按键位图 |
| 7 | 对字节 2～6 算 CRC-8，poly `0x07`，初值 0，无反射，无最终异或 |

位 0～8 依次为左、右、上、下、射击、开始/重开、暂停、自动演示、密度切换；其余位出现时拒绝整帧。零状态、序号零的报文是 `A5 5A 01 03 00 00 00 58`。

单字节绝不直接当按键；只在版本、长度、完整帧、CRC 和位图均正确时更新状态。UART 每轮最多接收 64 字节，避免输入洪泛无限阻塞游戏。半帧间隔超过 100 ms 被丢弃，超过 250 ms 未收到有效快照则释放全部按键。坏帧不延长持有时间。断线自动释放属于游戏输入策略，不等于通信可靠性保证。

电脑端仅需可选依赖 `pyserial`（本次未安装）；可用 `python -m pip install pyserial` 安装到自己的工具环境。它使用 Python 标准库及 pyserial 接口，不参与板上运行。先关闭占用该串口的终端，再执行，例如：

```text
python tools/uart_bridge.py --self-test
python tools/uart_bridge.py --port COM6
python3 tools/uart_bridge.py --port /dev/ttyUSB0
```

WASD/方向键移动，Z 射击，空格切换持续射击，Enter 进入手动玩法/重新开始，P 暂停，M 自动演示，K 切换 128/256/512 档，Q 退出并发送释放报文。电脑终端无法报告真正的松键，移动键依赖重复输入并在 180 ms 内无重复后释放；初次按住至系统重复之间可能短暂停顿。需要精确操作时可另写有 key-up 事件的前端，保持相同完整快照协议。脚本模式例子：`--keys 0x10 --duration 10`，持续发送 FIRE 10 秒后释放。

## 节拍、诊断与验证范围

计时来自 CLINT 的单调原始 tick。逻辑累加真实经过时间，每次 `game_step` 固定代表 1/60 秒，渲染目标为每秒 30 次。调试器暂停或过载时最多追赶 8 次逻辑步并丢弃额外积压，不会无限追赶；UART 遥测 `late` 记录这种降速。此调度不保证 100 MHz CPU 在所有弹量下达到目标频率。

遥测字段均为十六进制：`tick` 是当前局模拟步数，`enemy` 是活动敌弹数，`render_total` 是累计 CPU 渲染调用次数，`late` 是累计积压计数，`hash` 是游戏状态哈希，`rx` 是有效输入帧数。RAM 诊断另外输出 `frame_hash`，逐像素读取最近绘制的帧，验证 RAM 像素运算；哈希本身也有诊断开销。它们不是显示 FPS；状态结束或暂停时 tick 不再前进。

本轮在 Windows GCC 15.2 上实际通过 UART 单元测试（`-std=c11 -O2 -Wall -Wextra -Werror`），Python 3.12 实际通过协议自测和字节码语法检查。`sapphire_main.c` 对真实 BSP 头文件做过电脑 GCC `-fsyntax-only`；原 BSP 有注释/未使用变量警告。这不是 RISC-V 链接，更不是板测。板上验证和真实显示适配仍待完成。
