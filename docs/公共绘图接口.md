# 公共绘图命令与 CPU／G2D 执行接口（2026-10-26）

## 一份场景，两种执行器

```text
Game（难度、弹幕强度、对象和界面状态）
  → game_build_commands：400×300有序Fill／Copy，只写命令元数据
  → game_hardware_commands：换成对齐素材视图，居中到640×480
  → CPU目标：gfx_cpu_submit_context → 自有RAM画布
  → FRAME目标：gfx_g2d_submit → BEGIN／全屏Fill／原序绘图流／END
  → 公共job轮询 → render／presented／health／旧front释放确认
```

`src/render.c`只决定画什么、源矩形、目标位置和遮挡顺序；逐像素循环在同级库 `backends/cpu.c`。`src/hardware_assets.c`完成一次性素材打包及命令转换，`src/hardware_render.c`负责双后端和显示发布。库源码由 `GFX_ROOT`直接引用。

电脑版保留400×300 CPU窗口／PPM入口。板端使用640×480画布，原场景平移`(120,90)`，第一条Fill扩成640×480，其余命令保持源区域与绘制顺序，不缩放、不少画子弹。

## RGB565与目标语义

- `GFX_RGB565_LE`：R[15:11]、G[10:5]、B[4:0]；红`0xF800`存成`00 F8`。图像`stride/bytes`为字节，矩形和坐标为像素。
- Fill：`operation=GFX_FILL`、`flags=0`，color为原始16位值。超出`0xFFFF`返回UNSUPPORTED。
- Copy：同格式，源区域由`source_x/source_y + rectangle.width/height`指定，目标由`rectangle.x/y`指定；不隐式转换格式。
- 色键Copy：`flags=GFX_COLOR_KEY`，完整16位源像素等于key时保留目标，未命中原字节复制；超宽key拒绝。
- 公共565 Alpha／Key+Alpha不支持。已有8888和显式CPU-only565功能保留，但不混进本游戏的硬件命令。
- CPU目标显式为`GFX_DESTINATION_CPU`，需要有效像素指针；硬件目标显式为`GFX_DESTINATION_FRAME`，使用`gfx_g2d_frame_canvas()`的逻辑640×480图像，无CPU目标指针。

`game_hardware_target`先整批预检再统一改目标；转换不改变源图、源矩形、坐标、颜色、色键及顺序。CPU后端拒绝FRAME目标；公共操作值不直接当硬件opcode。

原数值uint16素材只在小端PC／RV32上直接解释；大端明确拒绝。硬件打包的每行stride向16字节对齐，每个allocation向64字节对齐并保留尾部padding。11个图片／字库源共252672B；另登记自有CPU画布作为第12个DMA只读源。CPU和G2D均使用相同的打包视图。

## 裁剪、顺序与容量

逻辑战斗区为`[12,281) × [12,287)`；移到板端后为`[132,401) × [102,377)`。裁掉左／上部分时同步增加source_x/y，再由公共库联合裁剪。精灵不会进入侧栏。顺序为背景→玩家弹→Boss→全部敌弹→玩家→保护框／中心点→边框／HUD→标题／暂停／结束遮罩。字库一字一次Copy，透明关系不重排。

`GameDrawList`固定864槽：512敌弹＋64玩家弹＋32场景预算＋256字形预算。全部576颗可见弹和完整界面的合成最大814条。包含第3600tick结束覆盖界面的高档完整DEMO峰值601条；旧552来自不含终局的奇数tick抽样。

公共G2D软件快照上限扩为`GFX_G2D_MAX_COMMANDS=1024`，游戏仍只预留864；硬件accepted−retired窗口仍最多16，asset registry与缓存范围表仍各64。不会把大场景拆成每颗子弹一个job，也不扩大硬件FIFO。

构建溢出普通失败清count=0，整帧失败不得提交；生成器拒绝列表与Game／目标别名时保持双方不变，因此必须检查返回值。CPU整批校验失败不写目标；G2D整批源映射／校验／发布先于BEGIN。硬件执行失败不承诺像素回滚，程序停止发布后续帧并保留取证信息。

## 三种板端模式与公平比较

| 模式 | 场景绘制 | 显示发布 |
|---|---|---|
| 1 CPU | 864槽内的完整命令由CPU context执行到自有640×480 RAM | 公共G2D job：全屏Fill＋普通全屏Copy，后端补BEGIN／END并确认FRM |
| 2 G2D | 同一场景命令转换为FRAME目标，由真实公共G2D job执行 | 同一个job完成END、呈现、健康和旧前台释放 |
| 3 比较 | 冻结一份命令，先CPU执行；CPU发布完成后，仅切target再原生G2D执行 | 两个连续确认的硬件帧，CPU在前、G2D在后；不是并排 |

模式3期间Game可以继续推进，但原生G2D阶段不会重新从Game构建场景。输入1／2／3仅改变下一次IDLE开始的选择；不清场、不改变难度／强度、不释放在途资源。模式1仍含硬件显示搬运成本，不能称为完全无G2D的显示路径。

本轮没有输出加速比。比较须固定同一配置、强度、输入、场景和完整命令，不能少画、改判定或改变画质。测试中的软件协议解码不等于读取真实硬件像素。

## 工作区与任务生命周期

两个context、命令列表、素材、CPU画布和设备对象均为持久独占静态存储。初始化先拒绝元数据／像素／CPU工作区／G2D工作区的非法别名；不能重新init取消任务。

| RV32存储 | 字节 |
|---|---:|
|单条公共命令|96|
|864条生成命令（属于renderer对象）|82944|
|CPU工作区静态预留|90112|
|G2D工作区精确需求|126504|
|G2D工作区静态预留|128512|
|打包DMA素材|252672|
|自有CPU画布|614400|

G2D精确工作区为2088B头部＋864×(96B命令快照＋44B显式编码＋4B序号表)。`GFX_G2D_CONTEXT_BYTES_BOUND`使用4096B保守前缀；CPU宏也为保守上界，内部包含命令快照和范围预检表。两宏仅适用于可信的小编译期容量，不做动态乘加溢出检查；初始化继续用requirements核对精确值和对齐。完整应用占用以ELF manifest为准，不能把上表当全部RAM。

初始化、逐帧提交、等待与release不调用分配器。原公共动态submit仍保留分配，游戏使用固定context路径。源码内存预算必须包含库工作区，不能只数Game对象。

CPU画完后，画布作为DMA只读源发布；直到该job确认完成并release后才允许下次CPU改写。原生G2D只读打包素材。所有模式共用一个设备／context／FRM捕获者，CPU不直接写硬件A/B或扫描中的FRONT。新帧只有真实presented身份和计数推进才累计；同front反复扫描不算新帧。

PENDING或超时不是取消。故障保留job、命令、源、目标和租约，禁止重提、补END、自动复位或释放仍在途资源；FAILED也可能无法release。成功时render、presented、health和旧front释放是不同证据，不能用队列空或COMMIT成功代替。

## 真实发布与测量边界

匹配Sapphire为单hart、无MMU、4KiB写穿D-cache、64B行。运行时发布器采用实际`0x0000500F`全失效，再读取独占DDR缓存行制造真实读miss，利用已核对桥的同source写响应排序排空之前CPU写入，最后保持MMIO顺序。没有使用缺证据的CSR0x810，也没有把空clean回调当成发布。构建前后以12文件哈希门控对应RTL/BSP；具体证据在runtime的`HARDWARE_ADAPTATION.md`与`publish_contract.json`。

这条发布路径只用于CPU拥有且设备只读的源，不提供硬件结果invalidate／acquire，不读扫描中的FRONT。DDR永久不响应时，同步排空读可能永久阻塞，软件帧超时不能抢占一次不返回的总线访问；实际DDR和位流仍待板测。

`cpu_draw_ticks`计从CPU提交前到完成／release后的区间，不含命令生成和显示搬运。`last_display`保存CPU帧搬运会话，`last_native`保存原生会话；G2D的prepare/cache/submit_poll/execution_wait/present_wait/health_wait为互斥软件观察区间，不是精确硬件执行周期。只有metrics enabled且valid时使用数值；日志含gpu_frame、gpu_valid和gpu_error，无效计时为NA。CPU序号与最后原生帧号应一起查看，不能把旧模式的历史值当成本次结果。

源码、主机CPU像素、协议替身／软件解码、交叉构建与板测分别记录。真实加速效果、DDR像素和HDMI帧率必须由匹配板卡上的实际运行确认。
